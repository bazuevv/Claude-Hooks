# Задержки webview при длинном ответе

Проверка 2026-09-18, расширение `anthropic.claude-code-2.1.269-win32-x64`.

## Подтверждённые наблюдения

В `.claude/hooks-runtime/webview-errors.log` теста с 14:47 по 14:58 (МСК)
лаг секундного таймера вырос от примерно 1 с до 6, 12, 22, 41 и 85 с.
В двух webview задержки практически совпадают, хотя DOM одного окна
оставался постоянным (2069 узлов). В изменяющемся окне было 890–1619 узлов.
Измеренные пользовательские обработчики заняли 324 мс за интервал с лагом
85 с; это не измерение всего JS, React, стилей или отрисовки браузера.

Старая сводка всегда подписывала интервал как 10 секунд даже при задержке
вызова отчёта. Теперь `interval_sec` содержит фактическую длительность,
а `nominal_interval_sec` — настроенный период 10 секунд.

Настройка `locale = "en"`, блок `claude-localizer` отсутствует в установленном
JS, `package.json` совпадает с английским оригиналом. Само состояние уже
загруженного окна проверяется полем `localizer_installed` после перезагрузки.

## Подозреваемая работа

В исходном bundle компонент `r$` передаёт весь текст в `b41` (react-markdown).
Тот создаёт цепочку unified и синхронно вызывает `parse`/`runSync`.
Компонент размышлений `rf1` создаёт содержимое Markdown независимо от того,
открыт ли `<details>`: свёрнутость сама по себе не исключает эту работу.
Имена относятся только к проверенной версии расширения.

Изолированный запуск того же парсера с GFM на данных сессии
`282576db-8ccc-4521-85fc-be159919fd52` дал:

| Текст | Символов | Один разбор |
|---|---:|---:|
| Ответ | 5 000 | 16 мс |
| Ответ | 20 000 | 53 мс |
| Ответ | 40 000 | 97 мс |
| Ответ | 49 833 | 103 мс |
| Размышления | 47 654 | 74 мс |

Это запуск native-парсера в Node VM с минимальной заглушкой DOM для
декодирования HTML-сущностей, без React commit/layout/paint. Результат
показывает рост стоимости полного разбора, но не доказывает, что именно
он вызывает минутную задержку таймера. В живом окне ещё нужно измерить
частоту повторных разборов, React и работу браузера. Нативный bundle для
эксперимента не менялся.

## Добавленная диагностика

Управляется существующим `perfProbe` в `claude-custom-config.toml`.
После перезагрузки окна отчёты `perf` содержат:

- `attribution_supported`: доступные `longtask` и `long-animation-frame`;
- `long_tasks`: число/сумма/максимум длительных задач и пять самых долгих;
- `long_frames`: пять самых долгих кадров, время блокировки и до пяти
  наиболее дорогих скриптов каждого кадра (функция, файл, смещение,
  invoker, длительность, принудительная раскладка);
- `visibility`, `focused`, `heap_mb`, `locale`, `localizer_installed`.

Объём выборки ограничен; текст сообщений и URL query не собираются.
При отсутствии API браузера базовая диагностика продолжает работать.
Если `perfProbe = false`, наблюдатели не запускаются. После лимита 60
отчётов наблюдатели длительных задач отключаются.

Для следующего измерения нужно перезагрузить окно VS Code и воспроизвести
длинный ответ. Отсутствие атрибуции само по себе не доказывает отсутствие
нагрузки: возможны ограничения API и несколько процессов отображения.

## Контрольный тест с активным окном, 15:26–15:36

Сессия `80da77b6-92de-4492-bcc5-cbb40aa11f39`, webview `5aee8d35`.
В отчётах на пике `focused=true`, `visibility=visible`,
`localizer_installed=false`. Лаг вырос до 9,1 / 14,9 / 24,8 / 44,7 / 89,5 с.
За интервал 90,442 с наши обёрнутые обработчики заняли 324 мс, а браузер
зарегистрировал 18 длительных задач суммарно на 1220 мс (максимум 194 мс).
Следующий интервал содержал задачу 226 мс. Атрибуции long-animation-frame
по-прежнему нет. Объяснение только уходом пользователя в другое окно
этот тест не подтверждает; точный источник пауз остаётся неизвестным.

Добавлен временный `perfNativeMarkdown=true` (работает вместе с `perfProbe`).
Он оборачивает проверенный компонент `b41` в том же модуле установленного
bundle и измеряет его прямые вызовы. `native_markdown_state` показывает,
подключился ли измеритель; `native_markdown` содержит число вызовов,
суммарное/максимальное время и максимальную длину текста. Это отдельная
метрика, не входящая в `ours_ms`. После лимита отчётов оригинал функции
восстанавливается; в неизвестной версии обёртка не устанавливается.
Дополнительно `stylesheet_links` проверяет гипотезу накопления CSS-ссылок.

Проверены сохранение результата/исключений функции, сброс интервала,
автоматическое снятие обёртки и подключение к реальному native-компоненту
из установленного bundle в изолированном VM. Живой профиль требует
перезагрузки окна с новым измерителем; измерение парсера не охватывает
последующий React commit и браузерную раскладку.

## Отложенная отрисовка свёрнутых размышлений

В установленном компоненте `rf1` тело `details` создаётся независимо от
`open`: скрытый `div` содержит `r$`, который вызывает Markdown-парсер.
Добавлен `lazyCollapsedThinking=true` в `claude-custom-config.toml`:
обёртка сохраняет вызов исходного компонента с его React-состоянием,
заголовком и обработчиком раскрытия, но не передаёт скрытое тело в React.
При раскрытии используется актуальный текст из исходных данных. Обёртка
не меняет поток ответа, историю или время завершения задачи.

`false` либо `safeMode=true` возвращают штатную обработку после Reload Window.
В неизвестном bundle обёртка не устанавливается. В perf-отчёте поле
`collapsed_thinking.state` показывает состояние, а `skipped` — суммарное
число пропущенных отрисовок скрытого тела с момента загрузки страницы.

Целевой тест `test_collapsed_thinking.cjs` проверяет отсутствие вызова
Markdown при свёрнутом блоке, свежий текст при повторном раскрытии,
управляемое и внутреннее состояние, отключение и неизвестную версию.
Прогон с путём к `index.js.original` выполнен на реальном коде `rf1`
с имитацией React hooks/JSX. Это проверка дерева компонентов, не замер
процента ЦП: эффект на живую нагрузку и лаг требует нового ответа после
Reload Window. Отрисовка раскрытых размышлений остаётся штатной.

## Объединение обновлений видимого Markdown

После включения отложенной отрисовки свёрнутого размышления пользователь
наблюдал 1,5–2% ЦП, при раскрытии — 9–10%. В свежем perf-отчёте webview
`0ee3d9b5` за интервал 52,721 с зарегистрировано 1835 прямых вызовов
Markdown-компонента, суммарно 30787 мс, максимум 58 мс на вызов, текст
до 39979 символов. Это подтверждает значительную нагрузку множества
относительно коротких разборов, которую longtask почти не показывает.

`markdownRenderIntervalMs=500` ограничивает обновление растущего текста
в `r$` двумя разами в секунду на блок. Между обновлениями сохраняется тот
же дочерний React-элемент, поэтому неизменившийся Markdown не разбирается
заново на каждом входящем фрагменте. Его собственное React-состояние
(например, меню ссылки) остаётся независимым. Таймер не переносится при
каждом фрагменте и получает последние данные; последний фрагмент выводится
даже при прекращении потока. Смена partial-флага и замена/сокращение текста
показываются сразу. Размонтирование, включая сворачивание размышления,
снимает таймер. Получение и запись ответа не меняются.

0 отключает оптимизацию, как и safeMode; применение — Reload Window.
Неизвестные компонент/алиасы React hooks пропускаются. Perf-отчёт содержит
`markdown_render`: состояние установки, интервал, накопленные количества
объединённых обновлений (`coalesced`) и публикаций (`flushes`).

`test_markdown_render.cjs` моделирует hooks и таймеры: 1500 фрагментов за
1,5 с дают 5 различных дочерних элементов с учётом исходного и последнего.
Проверены непрерывный поток, последний фрагмент без новых данных,
немедленное завершение, сохранение элемента при неизменном тексте,
актуальность контекста ссылок, отмена таймера и отключение. Прогон с
установленным bundle проверяет подключение к реальному `r$`, но не заменяет
измерения браузера. Процент ЦП и задержки после этой правки ещё предстоит
измерить на живом ответе.

## Почему первая версия ограничения не сработала

Повторный тест: `markdown_render.state=installed`, но `coalesced=0` и
`flushes=0`; за 51,223 с — 1957 разборов, 27903 мс Markdown. В исходном
bundle класс `kJ` вычисляет `key = hash + lastModifiedTime`, а assistant
рендерит `F(jK, ..., B.key)`. Каждый фрагмент меняет ключ React и создаёт
новый экземпляр блока: локальное состояние ограничения частоты теряется.
Предыдущий тест моделировал обновления одного экземпляра и этот случай
не покрывал.

Исправление при включённом `markdownRenderIntervalMs`: JSX-вызовы `jK`
для text/thinking со штатным изменяемым ключом получают стабильный ключ
по объекту блока (WeakMap). Исходная ревизия отдельно сохраняется в props:
сравнение memo учитывает её, поскольку исходный объект content изменяемый.
Ключи инструментов и явные ключи вложений не меняются. Проверяются сигнатуры
нативного memo и renderer; неизвестный bundle пропускается полностью.
Добавлены счётчики renders/mounts/unmounts/keyed_blocks. Тест проверяет
стабильность идентичности, обновление memo при изменении того же объекта,
разные блоки и сохранение сторонних ключей; выполнен и с реальным native
memo-компаратором из установленного bundle.

## Независимая запись нагрузки ЦП

`cpu_probe.py` запускается из UserPromptSubmit отдельным скрытым процессом.
OS-lock допускает один сборщик на проект для нескольких одновременных чатов.
Завершение отслеживается по серверному Stop (до 180 с дополнительной записи
отрисовки) и UI Stop; запоздалый UI Stop предыдущего сообщения игнорируется.
При потере событий действует cpuProbeMaxMinutes (120 минут). Отключение
cpuProbeEnabled прекращает сбор; интервал cpuProbeIntervalSec по умолчанию 2 с.
Зависимость — psutil; ошибку запуска сборщик пишет в журнал. Сессия/turn ID
и фаза есть у каждого снимка, текста и командных строк нет.

Журнал `.claude/hooks-runtime/cpu-usage.jsonl`, максимум 8 МБ и одна
ротированная копия `.1`. Служебные состояния — `cpu-probe-state/`.
Поля:

- `system_per_logical_cpu_percent`: общая нагрузка каждого логического CPU,
  индекс массива — номер CPU; сюда входят все программы.
- `vscode_cpu_percent_machine`: сумма Code-процессов, нормированная на число
  логических CPU; `vscode_cpu_percent_one_core` — сумма в масштабе одного CPU.
- `processes`: PID, роль (если доступна), обе шкалы нагрузки.
- `busiest_threads`: до 8 потоков с PID/TID и нагрузкой в масштабе одного CPU.
  Это не привязка потока к конкретному ядру: планировщик может переносить поток.
- `collection_ms`, `collector_cpu_ms`: длительность сбора и собственное CPU-время
  сборщика; последнее имеет дискретность системного учёта CPU.

На Windows используется один NtQuerySystemInformation-снимок всех процессов
и потоков, с проверкой границ буфера и идентичности PID. Обход psutil по одному
потоку оказался дорогим (сотни мс на снимок); на Linux используется psutil.
Роли процессов читаются один раз, недоступные обозначаются unknown.
Шкалы нагрузки: [psutil](https://psutil.io/api/#psutil.Process.cpu_percent);
структуры снимка: [Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntquerysysteminformation).

Проверка живого сборщика 18.09: 20 логических CPU, две тестовые сессии,
один процесс записи, два свежих снимка, максимум 7 мс на снимок.
Это проверка диагностики при малой нагрузке, а не подтверждение исправления
стриминга. Для сравнения нагрузки нужен следующий длинный ответ после Reload.

## Автопрокрутка после отложенной отрисовки

Пользователь подтвердил прекращение роста ЦП и постепенный вывод текста после
исправления ключей. Интервал `markdownRenderIntervalMs` уменьшен до 200 мс.
Добавлен `chatAutoScroll=true`: ResizeObserver следит за контейнером чата и
последними четырьмя непосредственными дочерними блоками. Изменения высоты
после отложенного React-обновления прокручивают чат до конца за один rAF.
MutationObserver отслеживает только добавление/удаление верхних блоков,
без наблюдения каждой текстовой мутации. История целиком не сканируется.

Ручная прокрутка вверх приостанавливает слежение; возврат вниз и кнопка ↓
возобновляют. При открытии истории вдали от конца позиция сохраняется,
при смене контейнера наблюдатели и обработчики снимаются. safeMode или
chatAutoScroll=false отключают модуль после Reload Window. Проверены
рост блока, пауза/возобновление, сохранение позиции, уборка обработчиков,
ограниченное число наблюдаемых элементов и интервал Markdown 200 мс.

## Вывод незавершённого абзаца, интервал 50 мс

По просьбе пользователя markdownRenderIntervalMs установлен в 50 мс.
В тесте сессии `57f979b4-01fb-4cac-b9a4-b9f70f6bc659` до этой смены:
202 CPU-снимка, средняя нагрузка Code 2,14%, медиана 1,84%, максимум 9,53%.
Это замеры предыдущей настройки, а не подтверждение нагрузки при 50 мс.

Найден дополнительный источник скачков: `r$` для partial-ответа вызывает
`wL0`, которая удаляет последний абзац после разбиения по пустым строкам.
При следующем абзаце накопленный текст становится видим целиком.
Настройка `markdownShowPartialParagraph=true` обходит только этот фильтр
на входе в отрисовку; оригинальный partial-флаг сохраняется во входящих
props и состоянии ограничения частоты. Получение данных, распознавание
завершения и немедленный финальный flush сохраняются. false возвращает
штатное ожидание абзаца. Зависимость — включённое ограничение частоты;
применение после Reload Window.

Целевой тест воспроизводит обрезку на реальных `r$` и `wL0` из установленного
bundle, проверяет полный незавершённый абзац с новой настройкой, отключение,
сохранение входного partial-флага и интервал 50 мс. Искусственной очереди
посимвольного вывода нет: если сам провайдер прислал большой фрагмент
одним пакетом, он показывается на ближайшем обновлении.

## Вывод последнего слова целиком

`markdownWholeWords=true` сохраняет незавершённый последний токен только
в исходных данных, пока не придёт пробел/перевод строки. Для отображения
используется префикс до последней границы пробельного символа. Такой подход
не угадывает завершение чисел, дефисных слов и URL по знакам пунктуации.
На окончании ответа весь текст выводится немедленно. Для размышления
передаётся отдельный display-флаг из `rf1.isCurrentlyThinking`, поскольку
его Markdown-компонент штатно не получает `isPartialText`.

Пока меняется только удержанное слово, сохраняется тот же React-элемент:
Markdown не разбирается повторно. Полученный текст не мутируется, история
не обрезается. Интервал остаётся 50 мс; настройка выключается через false,
зависит от markdownRenderIntervalMs > 0. Проверены кириллица, скобки,
цифры, перенос строки, NBSP, emoji, первое и последнее слово без пробела,
сохранение исходных props и немедленное завершение ответа/размышления.

## Вывод завершёнными предложениями

Включён `markdownWholeSentences=true`, приоритет выше markdownWholeWords.
Границы определяются Intl.Segmenter для русского текста; подтверждение —
конечная пунктуация с последующим пробельным разделителем. Добавлена
проверка распространённых сокращений и номеров пунктов. Числа и доменные
имена не режутся по внутренней точке, кавычки сохраняются. Unicode-многоточие
нормализуется только для поиска границ, исходный текст не изменяется.
Внутри незакрытого Markdown-кода граница не публикуется.

Обрабатывается только ещё не показанный хвост; готовый префикс сохраняется,
а одинаковый отображаемый текст не вызывает новый разбор Markdown.
На завершении ответа и размышления буфер выпускается полностью даже без
последней точки. Интервал остаётся 50 мс, применение — Reload Window.
false возвращает прежний режим слов/фрагментов по соответствующим флагам.
В perf-сводке режим виден как `markdown_render.whole_sentences`.
Целевые тесты прошли на установленном renderer, включая незавершённое
предложение, неизменность React-элемента, числа/домен, сокращение, кавычки,
многоточие, открытый код и финальный остаток обоих типов текста.

## Адаптивная анимация завершённых предложений

`markdownAnimateSentences=true` включает постепенное раскрытие уже готового
префикса предложений. false оставляет прежнее появление целыми предложениями.
Зависимости: markdownWholeSentences=true и markdownRenderIntervalMs > 0.
Изменение применяется после Reload Window.

Каждый блок измеряет прирост входящего текста и сглаживает скорость получения.
Темп вывода выбирается по этой скорости, паузам и размеру оставшейся очереди.
Во время потока сохраняется запас для неравномерного поступления текста. После
завершения потока финальный остаток допечатывается не дольше 3 секунд.
Время выполнения задачи и сохранённый ответ не меняются: очередь относится
только к отображению. При занятости/скрытии страницы таймер не гарантирует
трёхсекундный срок; после возобновления вывод догоняет актуальные данные.

Анимация обновляется не чаще раза в max(50, markdownRenderIntervalMs) мс,
не создаёт таймеров в ожидании незаконченного предложения, очищается при
размонтировании и замене текста. Готовая история и содержимое при повторном
открытии блока не проигрываются с начала. Intl.Segmenter с granularity=grapheme
не позволяет разрезать составной emoji или букву с комбинируемым знаком.
Новый Markdown строится на обновлениях видимого префикса; отдельного DOM
наблюдателя на буквы нет, штатная автопрокрутка следует за ростом блока.

Perf-сводка содержит animate_sentences, animation_ticks, animation_rate,
animation_receive_rate и animation_max_queue без содержимого текста.
Проверены постепенный вывод после завершения предложения, адаптация к
разной скорости поступления, плавный вывод большого пакета, Unicode,
финальный остаток ответа/размышления, открытие истории, замена сообщения,
снятие таймеров и отключение режима. Живая нагрузка новой анимации пока
не измерена; измерения CPU уже включены для следующего ответа.

## Учёт пауз в анимации

Убран секундный срок опустошения очереди во время незавершённого ответа:
он заставлял печать обгонять сервер. Теперь этот срок действует только после
финального признака ответа/размышления. Оценка поступления сглаживается на
интервале около 4 секунд и снижается при отсутствии пакетов, даже если новые
React props не поступают. Отдельно учитываются промежутки между пакетами и
выпуском завершённых предложений. Последние длинные паузы постепенно забываются.

Запас рассчитывается на 2–15 секунд; по мере его истощения печать замедляется.
Во время потока минимальная скорость — 50 единиц UTF-16 в секунду, верхнего
предела нет (см. ниже управление запасом в 500 символов). Составные символы
выводятся целиком. Бесконечную паузу сервера скрыть невозможно: при исчерпании
готового текста печать всё равно остановится. Новых DOM-наблюдателей нет,
частота кадров прежняя. Расчёт хранит фиксированное число счётчиков на блок.

В perf-сводку добавлены animation_reserve_ms и animation_receipt_pause_ms.
Целевой тест моделирует большой пакет, пять секунд без поступлений, снижение
темпа, возобновление потока и быструю выдачу всего остатка только после финала.
Также проверяются Unicode, история, замена текста, размышления и очистка таймеров.
Живой темп и нагрузку после изменения нужно оценить при следующем ответе.

## Видимый буфер и нижний предел скорости

Включён debugOverlay в claude-custom-config.toml. Панель в правом верхнем
углу показывает буфер даже в свёрнутом состоянии: оставшееся число символов,
шкалу относительно максимального размера текущей очереди, готовый к печати
остаток и текст, ожидающий окончания предложения. После опустошения шкала
нулевая; новая очередь начинает собственный отсчёт максимума. Размер не является
фиксированной ёмкостью: это фактически полученный, но ещё не показанный текст.
Счётчики суммируются для смонтированных блоков ответа и раскрытого размышления
в данном webview. Закрытые размышления без renderer в буфер не входят.

Новые поля markdown_render в ограниченном perf-журнале webview-errors.log:
animation_queue, animation_ready_queue, animation_waiting_sentence,
animation_queue_peak, animation_min_rate. Они считаются в единицах UTF-16,
без сохранения содержимого текста. Изменения учитываются при получении,
печати, замене и размонтировании; подсчёт не обходит DOM и другие блоки.
Панель обновляется каждые 500 мс, неизменные значения не переписывает.
Все новые DOM-узлы помечены __claudeOwnNode для исключения из наблюдателей.
debugOverlay=false полностью отключает панель; применение — Reload Window.

Нижняя скорость при наличии готового текста — 50 символов/с. Снижение оценки входящего
потока не может опустить печать ниже этого порога. Финальный признак ответа
по-прежнему освобождает незавершённое предложение и быстро допечатывает хвост.
Порог не создаёт отсутствующий текст и не отменяет ожидание границы предложения.

Целевой тест воспроизводит минуту без пакетов, поступление небольшого запаса,
затем проверяет прирост не менее 249 символов за следующие 5 секунд с учётом округления и финальное опустошение
буфера. Проверены актуальность счётчиков, очистка после замены/размонтирования,
шкала, отключённое состояние и отсутствие повторных DOM-записей панели.
Это автономные проверки; живую остановку ответа и нагрузку после включения
панели предстоит оценить в следующем пользовательском тесте.

## Автоскорость без потолка, ориентир 500 символов

Удалены ограничения 60 символов/с на вывод и 120 символов/с на оценку
поступления. Минимум — 50 символов/с. animation_buffer_target=500 задаёт
ориентир готового к печати остатка, а не жёсткую ёмкость и не обрезание текста.
Незавершённое предложение может временно увеличить общий буфер сверх ориентира.

При остатке Q базовая скорость учитывает сглаженное поступление и запас на
наблюдаемые паузы. К ней добавляется max(0, Q − 500) / 0.5 символов/с.
Поэтому большая очередь ускоряет вывод без фиксированного потолка, а при
уменьшении очереди ускорение плавно исчезает. Под непрерывной высокой нагрузкой
и при пакетной доставке фактический запас может быть немного выше 500.
Финальный признак запускает допечатывание всего хвоста не дольше 3 секунд.
Обновление Markdown остаётся раз в 50 мс; отдельный таймер на каждую букву
не создаётся. Панель показывает новый минимум и ориентир запаса.

Проверены очередь около 7000 символов, её уменьшение до примерно 500 за
несколько секунд, рост скорости для вдвое большей очереди, отсутствие
накопления тысяч символов при непрерывном потоке около 800 символов/с,
минимальный темп после паузы, финальный сброс и диагностика буфера.

## Освобождение остатка при остановке сессии

Причина зависания с «К печати: 0»: при interrupt блок kJ может сохранить
isPartial=true и не получить content_block_stop. Ожидание конца предложения
продолжалось, даже когда сессия уже остановлена и продолжение не придёт.

Адаптер Nn0 передаёт идентичность блока в renderer ответа/размышления.
Перехватываются нативные yQ.interrupt и yQ.endTurn с проверкой сигнатур;
их вызовы, аргументы и возвращаемые значения сохраняются. По messages данной
сессии через WeakMap уведомляются только renderer её блоков. Резервный путь —
переход busy=true → false в существующем наблюдателе времени сообщения.
Состояние нативного блока и содержимое ответа не изменяются. WeakMap хранит
границу завершения блока с причиной, сессией, номером запроса и полученным текстом;
повторные уведомления не продлевают срок допечатывания.
Регистрация удаляется при размонтировании. Новых опросов DOM/таймеров нет.

После остановки полностью освобождается даже незавершённое предложение;
ожидающий renderer пробуждается и при отсутствии таймера анимации. Скорость
старта финального вывода — максимум из предыдущей скорости × 1.15, минимума
50 символов/с и остатка / 3 с. Далее скорость не снижается. На последнем кадре
по истечении 3 секунд остаток выпускается целиком. Ограничения задержек JS
в заблокированном/скрытом webview остаются прежними.

Perf-поля animation_end_binding и animation_end_events показывают установку
перехватов и количество уведомлений. Тест использует реальные Nn0, rf1,
interrupt и endTurn из установленного bundle: незавершённый хвост без таймера,
сохранившийся partial=true, повторное событие, остановку другой сессии с тем же
текстом, раскрытое размышление, ускорение большого остатка и полную выдачу
не позднее 3 секунд. Проверки автономные; живую остановку проверяет следующий запуск.

## Возобновление потока в той же вкладке

В предыдущей правке остановка сохранялась навсегда для объекта блока.
Кроме того, endTurn вызывается внутри resetPerProcessState при замене процесса,
а не только при result. Последующие пакеты отмеченного блока обходили фильтр
предложений, а ветка «не streaming до и после» выводила их мгновенно.
Это воспроизводится без клика Стоп: сброс процесса → продолжение того же блока.

Теперь внутренний endTurn при resetPerProcessState не завершает анимацию;
его отложенный busy=false также исключён из резервного пути. При обычном
endTurn учитывается предыдущее busy=true. Маркер завершения снимается, если
активная сессия снова присылает текст незавершённого блока. Для явного interrupt
требуется новый sendTurnIdx: запоздавший пакет отменённого запроса остаётся
частью финального допечатывания, а не новым ответом.

Состояние React используется только для пробуждения renderer, а не как вечный
флаг остановки. Уже напечатанная часть не исчезает, когда возобновлённый поток
снова ждёт окончания предложения. Поздние пакеты после реального окончания
добавляются в анимацию с прежним трёхсекундным сроком; отдельная ветка мгновенного
показа остаётся только для истории, которая никогда не была потоком.

Новые счётчики perf: animation_resumed и animation_reset_ends_ignored.
Тесты воспроизводят сброс процесса без Стоп, возобновление после endTurn,
новый запрос после interrupt в том же блоке/вкладке и запоздавший пакет
отменённого запроса. Проверены ожидание целого предложения, движение букв
между пакетами, отсутствие отката видимого текста и последующее завершение
за 3 секунды. Живого воспроизведения в текущем webview пока нет.

## Редкие таймеры в видимом webview (19:03–19:04)

В webview-errors.log за 2026-09-18 19:03:52: visible=true (visibility=visible),
focused=true, lag.max=1005 мс, только 5 тиков секундного таймера за 9.993 с.
При этом long_tasks=0, long_frames=0, ours_ms=12, native Markdown max=6 мс.
Renderer смонтирован один раз, без размонтирований, animation_end_events=0;
анимация успела сделать всего 6 шагов. К 19:04:02 было 16 шагов,
задержка секундного таймера снова около 1000 мс. Эти данные указывают на
редкое обслуживание таймеров, а не на дорогой разбор Markdown. Точную
внутреннюю причину ограничения таймеров в VS Code журнал не устанавливает.

Coalescing и анимация переведены с setTimeout на requestAnimationFrame:
callback проверяет срок кадра, вывод сохраняет интервал не меньше 50 мс.
Без API кадров остаётся совместимый timeout-fallback. Планирование существует
только при незавершённой работе; при опустошении очереди и размонтировании
оно прекращается. Нет опроса DOM или дополнительного парсинга на каждом RAF.

Убраны две ветки мгновенного выпуска очереди при visibilityState=hidden.
Браузер приостанавливает RAF скрытой страницы; накопленный текст остаётся в
очереди. При возобновлении незавершённого ответа шаг расходует не больше
100 мс времени печати (либо настроенного интервала, если он больше).
Пропущенные секунды не превращаются в большой скачок. Автоматическая скорость
по размеру очереди, минимум 50 и финальное ускорение за 3 секунды сохранены.

Диагностика: animation_scheduler, animation_frame_max_gap_ms,
animation_late_frames. Тест моделирует таймеры с минимальной задержкой 1000 мс
при нормальных кадрах, скрытие на 10 секунд, задержку кадра на 5 секунд,
возврат, финальную выдачу и отмену RAF при размонтировании. Все целевые
проверки прошли. Реальную частоту кадров и нагрузку после установки нужно
подтвердить следующим пользовательским прогоном.
